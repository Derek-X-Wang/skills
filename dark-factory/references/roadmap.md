# Roadmap and promotion gates

Use to plan the next capability or propose broader decision authority. This is an on-demand planning guide, not an instruction to activate features or launch work. Keep current readiness and evidence in private run/project records; an installed skill or completed design is not an operational milestone.

## Two independent tracks

- **Operational capability:** reliable execution, manual continuation, useful parallel work, recurring triggers, remote execution, and automatic recovery.
- **Decision authority:** which choices and external actions the owner has delegated for a particular project/workflow.

Operational progress never widens decision authority. Personal and company workflows can retain different permissions at every milestone. Within an already approved personal goal, autonomous task selection and ordinary implementation decisions are already allowed; do not ask again merely to earn a higher level. Bite keeps its private-review/local-fix endpoints until the owner explicitly changes the applicable authority and company rules permit it.

## Operational milestones

### M1 — prove the smallest real loop

Choose one explicitly authorized pilot project and one bounded useful task. Configure its private records, exact executor, quota reserve, required review/checks, and permitted endpoint. Start with the smallest necessary action scope.

Promotion evidence: actual task execution and verification, a readable checkpoint, identified resource ownership, retained artifacts, and a completed cleanup/retention report. Record actual human interventions and any unexpected behavior. Label simulations separately. A real one-shot Bite pilot may be evaluated independently under its company restrictions.

### M2 — prove manual continuation: Stage B

On that same machine, manually start a new manager session, then a different supported harness. Follow [continuation](continuation.md). Demonstrate that the new manager can establish current state rather than merely repeat the prior summary.

Promotion evidence: a real cold read of private records, verified old-manager/writer fencing, one current owner, preserved dirty work and budgets, fresh target/tool readiness, and completion of an unfinished authorized task without duplicate work. Exercise an old worker remaining active and an uncertain external action using a disposable authorized target or controlled fixture; report which evidence is live. If a needed control-plane action is unavailable, retain the manual boundary and record the missing capability.

### M3 — prove useful parallelism and pacing

Run independent authorized projects under one global manager with separate execution owners. Start from a small pilot allocation and increase it only while observed capacity supports the work. Apply explicit priority overrides and [capacity policy](capacity-and-fleet.md).

Promotion evidence: useful verified outcomes, shared-pool commitments accounted for, correct short/weekly/model limits, preserved interactive reserve, measured consumption, and sensible admission changes as reset approaches or capacity falls. Demonstrate sprint expiry restoring normal policy and review/integration capacity keeping up with implementation. Stop adding concurrency when it produces more waiting or rework rather than more useful output. Hardware tests must respect the owner's declared load limits.

### M4 — optional capability branches

These can be added independently; none requires Stage C or every other branch:

- **Recurring intake:** attach an authorized existing trigger to the proven one-shot workflow. Verify event delivery, pagination/deduplication, changed-head handling, overlap prevention, trigger ownership, and a supported disable path. Begin with limited frequency and permitted private outputs.
- **Cross-machine execution/continuation:** verify each exact remote route, data boundary, checkout, return path, cancellation/cleanup, and state affinity. A remote shell or a copied configuration does not prove an authenticated desktop is transferable. Prove one bounded task/transfer before expanding the target set.
- **Additional model/harness/provider:** verify entitlement, tools, actual model/effort, task fit, and return route; record dated observations. Trial newly eligible options only within their permitted roles. New catalog entries do not automatically become reviewers or defaults.

### M5 — autonomous manager recovery: Stage C

Attempt only after the relevant Stage B continuation path works and a real supported liveness/launch/control mechanism exists. Record exact authority to detect failure, fence the old owner, launch a replacement, carry the checkpoint, and stop after a bounded recovery budget.

Promotion evidence: controlled manager failure followed by a verified replacement; active old workers remain exclusive; stale observations, uncertain actions, consumed redemption grants and hard STOPs survive recovery correctly. Failure to prove ownership or current authority must leave dependent work parked, with evidence available for manual recovery. Demonstrate the stop/disable and manual fallback paths before unattended use. A timer, heartbeat, or JSON epoch alone does not satisfy this gate.

## Improving judgment without silently expanding authority

For decisions already within scope, use existing risk-appropriate review and compare actual outcomes with the owner's preferences. When the same missing decision policy repeatedly requires owner input:

1. Record the situation, proposed decision, alternatives, evidence, actual owner answer and outcome in private records. Separate missing authority from a skill defect or an ordinary implementation choice.
2. Propose one precise class of standing decisions, with allowed context, exclusions, acceptance evidence, and a recovery path. For example, a future change to which Bite review comments may be posted needs its own owner decision; reliable intake does not grant it.
3. Evaluate that proposed class against representative prior cases and difficult counterexamples. Declare coverage and uncertainty; avoid claiming that one successful result establishes general judgment quality.
4. Obtain owner approval for the specific authority change, apply the relevant review budget, and record the approved policy/version before using it. Expand one class at a time and retain the previous narrower policy.

Model agreement helps assess a decision; it does not grant authority. Deployment, paid spend, new projects, company actions and external human replies retain their applicable approval rules.

## Promotion packet and readiness record

At a meaningful handback, propose the next useful milestone only when its prerequisites have evidence. The manager prepares a compact packet:

- Capability or decision class, affected project/workflow, exact route and proposed pilot scope.
- Evidence references, real versus simulated coverage, observed failures, interventions, and remaining unknowns.
- Quota/time/spend/concurrency limits, required checks/review and stop conditions.
- Existing authority reference; explicit owner decision for any newly required authority.
- Pilot owner, acceptance criteria, supported fallback and recovery artifacts.

Keep an evidence-backed readiness entry per capability/route/workflow, for example `not_run`, `pilot`, `verified_within_scope`, or `blocked`, with verification time and next unresolved gate. Do not reduce the whole fleet to one maturity number or claim verified scope survives a material route/tool change without rechecking it. Select a trial and evidence sample appropriate to impact; this roadmap invents no universal run count, success rate or calendar deadline.

A next-level proposal is not self-authorization. Execute a pilot only within existing task authority or a specific owner grant. Larger implementation work enters the [maintenance queue](continuous-improvement.md) and receives the review its impact requires. After an actual regression, disable the affected capability through its supported owner mechanism, preserve evidence and use the last verified eligible path; unrelated authorized work may continue.
